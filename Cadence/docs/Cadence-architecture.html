How to read this diagram. Eight horizontal lanes. Top to bottom follows the request lifecycle: a Razorpay webhook hits row 2 (ingress), gets HMAC-verified, deduped, and appended to the row 3 event store with a SHA-256 prev-hash. The row 4 journey engine claims the task from the row 3 durable queue, rehydrates the journey from the event store, and runs the deterministic fast path: classify, score with the Recovery Brain (row 4, pink), floor with the phantom-failure guard, hand to the Policy Guardian (row 5, green). The Guardian returns one of 11 reasons; the engine emits an event and either enqueues a timer (row 3) or executes the intervention (row 6). Only one probabilistic edge exists: the unknown-cause ladder that calls the LLM chain (row 7) with a taxonomy-bounded JSON menu. The Guardian re-vetoes any LLM pick. Row 8 is the read-only surface: SPA (9 tabs, polls /api/* every 2.5s), MCP server (8 read-only tools), Supabase cloud mirror (one-way projection every 30s). Row 1 is the Razorpay network and the customer.

The four parallel recovery state machines (row 3, right) share the same Guardian + bandit + executor contract. They emit checkout.*, b2b.*, and mandate.* events into the same hash-chained audit log; the SPA's Checkout / B2B / Mandate tabs read them.
